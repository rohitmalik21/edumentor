EduMentor AI — Request Flow Architecture

Two independent entry points (Gradio UI + FastAPI REST) sharing a common service layer

Key Insight: Gradio UI does NOT call FastAPI via HTTP. Both are independent entry points that directly import and call the same Python service functions. They run as parallel servers (launched via run.py) sharing in-process memory (study material state, metrics singleton).

PATH A — GRADIO UI (Browser User)

GRADIO UI REQUEST FLOW

1 User → Gradio UI
User selects tab, enters input, and clicks action button
Learn: upload file / Practice: generate quiz / Ask: type question / etc.
2 Gradio UI ↵ UI handler
Gradio calls Python handler function directly (no HTTP)
e.g. ask_by_text(), process_upload(), create_quiz(), generate_summary()
3 UI handler → Service Layer
Handler imports and calls service function directly
answer_question(), summarize_material(), generate_quiz(), transcribe_audio(), simplify_concept()
4 Service → LLM Client
Service calls get_llm_response() via utils/llm_client.py
Routes to Gemini API, OpenAI API, or local FLAN-T5 based on Config.LLM_PROVIDER
5 LLM Client → Model
Load or reuse cached model, run inference
Local: load FLAN-T5 once → torch inference | Cloud: HTTP call to Gemini/OpenAI API
6 Model ← LLM Client
Generated text + token count returned
Decoded model output or API response text
7 LLM Client → Metrics
Record latency, tokens, success status to MetricsLogger singleton
metrics.log_request(service, latency, tokens_used, success=True)
8 Service ← UI handler
Service returns result dict: {"summary": "...", "error": False}
Structured dictionary with task output + error flag
9 Gradio UI ← User
Gradio renders result in UI components
Markdown output, audio player, textbox, or quiz display updated in browser
PATH B — FASTAPI REST API (External Client)

FASTAPI REST REQUEST FLOW

1 API Client → FastAPI
POST /api/v1/{endpoint} with JSON body or multipart file
curl, Postman, mobile app, or any HTTP client → Port 8000
2 FastAPI ↵ Pydantic
Validate request via Pydantic models
SummarizeRequest, AskRequest, QuizGenerateRequest — type checks, field constraints (ge, le)
3 FastAPI → Service Layer
Endpoint handler calls service function directly (same Python import)
Same functions as Gradio path: summarize_material(), answer_question(), generate_quiz()
4 Service → LLM Client
Service calls get_llm_response() → Model inference
Identical path as Gradio: LLM Client → Model → response → metrics logged
5 Model ← LLM Client
Inference output + metrics recorded
Same model instances and MetricsLogger singleton shared with Gradio path
6 Service ← FastAPI
Service returns result dict to endpoint handler
{"summary": "...", "error": False} or {"answer": "...", "relevance_score": 0.85}
7 FastAPI ← API Client
HTTP 200 JSON response via Pydantic response model
Serialized as SummarizeResponse, AskResponse, QuizGenerateResponse, etc.

CONTROLLED ERROR PATHS

A Gradio UI — Input / Service Failure
UI handler checks: empty input, missing material, no audio file
Returns user-friendly message: "Please upload study material first."
If service raises exception → caught in handler, returns error string
LLM Client retries rate-limit errors (429) up to 3 times with 15s delay
On final failure: metrics.log_request(success=False) → error displayed in Gradio output
B FastAPI REST — Validation / Service Failure
Pydantic validation fails → automatic HTTP 422 with field-level error details
Business logic check fails (no material loaded, bad file type) → HTTPException(400)
Service/model exception (API timeout, OOM, parse error) → HTTPException(500)
LLM Client retries rate-limit errors before raising RuntimeError
Metrics logged for failed requests: latency, tokens=0, success=False
Client receives: {"detail": "Error processing file: ..."}

FastAPI Endpoints Reference (Port 8000)

Method Endpoint Service Function Description
GET /health — Health check & config status
